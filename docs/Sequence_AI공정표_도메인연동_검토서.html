핵심 요약 — 세 가지 결론

리서치가 결정적 사실 하나를 확인해줬다: 당신이 원하는 "물량÷일작업량으로 공기 적정성 판정"은 이미 대한민국 법정 산정기준이며, 그 공식이 주공정선(critical path) 상의 작업에 한정된다 — 즉 우리 CPM 엔진과 정확히 맞물린다.

1

실시간 반영엔 MCP가 정답이 아니다

단일 로컬 앱이 스스로 반영하는 시나리오의 정석은 인-프로세스 함수콜링 + 결정론 엔진 + 사람 승인. MCP는 "여러 외부 AI 클라이언트가 공유"할 때의 도구고, 시간민감·결정론 작업엔 오히려 오버헤드다.[1][2]

이미 만든 검토 파이프라인을 로컬 호출로 승격
2

공기 적정성엔 "법정 공식"이 있다

「공공 건설공사의 공사기간 산정기준」(국토부고시 2024-1021호): 작업일수 = 물량 ÷ 1일 생산성(표준품셈), 주공정선 한정. 총공사기간 = 준비+작업일수+비작업일수+정리.[10][11]

우리 CPM·우기 밴드와 그대로 정합
3

표준 데이터: 공식은 있으나 "깨끗한 DB"는 없다

표준품셈은 data.go.kr에 무료·무제한 라이선스로 있으나[7], 공종별 "일작업량"을 바로 쓸 수 있는 형태는 아님(검증에서 기각). 문서에서 추출·구조화 + 조달청 공종코드 매핑이 실제 과제.[13]

DB 구축이 이 프로젝트의 진짜 노동

⚖️ 이 검토서를 관통하는 한 문장

"법정 공사기간 산정식(물량÷일작업량, 주공정선 한정)을 표준품셈 로컬 DB로 계산해, 막대 클릭 시 근거로 띄우고, AI 제안은 로컬 함수콜링으로 받아 결정론 엔진이 재계산 후 화면에 즉시 반영한다."
— MCP는 나중에 외부 에이전트용 어댑터로만. 코어는 우리가 이미 절반 지었다.

01

현황 진단 — 어디에 붙나

코드 실측 기준. 스케줄 코어와 AI 검토 골격은 있으나, 도메인 데이터(물량·공종코드·표준 일작업량)와 실시간 호출 경로는 전면 공백이다.

✅ 이미 있는 것 (붙일 자리)

  • CPM 엔진 — 주공정선·여유 자동 계산 engine/scheduling.ts → 법정 "주공정선 한정" 공기 검증과 정합
  • AI 검토 라운드트립 — buildReviewPlan/applyReviewDeltas·ReviewDialog(방금 구축) → 실시간 경로의 재사용 코어
  • 공정 클릭 → Inspector 「공정 속성」 탭 Inspector.tsx → "근거 팝업"이 얹힐 자리
  • 시설물 표준 공정 템플릿(33+9종) → "유사 실적·표준 대비" 판정의 기반
  • 우기(강우) 밴드 RainySeason → 법정 "비작업일수(기상)"와 연결점

❌ 없는 것 (추가 대상)

  • 물량·단위·공종코드 데이터 모델 — Task에 수량 필드 없음 → 산정식 계산 불가
  • 표준 일작업량(생산성) 로컬 DB — 표준품셈 기반 기준 데이터 없음

  • 막대 호버 툴팁 — 현재 바에 hover 팝업 인프라 없음(신규)
  • 실시간 LLM 호출 경로 — 지금은 .md 수동 왕복. 앱 내 직접 호출 없음
  • 적정성 판정 엔진 — 4방식(산정식·표준대비·법적준수·LLM) 없음
02

Part A · 실시간 AI 반영 — MCP냐 다른 방법이냐

직접 물으신 것: "MCP를 붙이면 되냐, 아니면 다른 방법이냐?" 리서치 결론은 명확하다 — 이 시나리오의 정답은 MCP가 아니다.

결정 휴리스틱: "호출자가 누구냐"로 갈린다

방식언제 맞나Sequence 적합성
인-프로세스 함수콜링 단일 앱 하나만 그 로직을 쓰면 됨 — 앱 내부에서 LLM이 도구(함수)를 호출[1] ✓ 최적 (권장)
로컬 REST API 비(非)LLM 호출자(서비스·크론·웹훅)나 시간민감·결정론 작업 — 예측 가능한 성능[1] 보조 (서버 프록시)
MCP 여러 외부 AI 클라이언트(Claude Desktop 등)가 같은 도구를 공유해야 할 때. 프로토콜 오버헤드 존재[2] ✕ 코어엔 과함 · 향후 어댑터

핵심: "검토 누르면 이 앱 화면에 즉시 반영" = 단일 앱 내부 시나리오. 여기에 MCP를 쓰면 프로토콜 계층만 늘고 얻는 게 없다. MCP는 "시간민감·결정론 작업엔 직접 호출이 더 예측 가능"[1]하다는 원칙에 정면으로 걸린다. 만약 MCP를 쓴다면, 로컬 단일 사용자엔 stdio 트랜스포트가 정석(네트워크·소켓·인증 불필요)이나[3], 그건 외부 AI를 붙일 때 얘기다.

03

Part B · 도메인 연동 + 공기 적정성 검증

공정표는 수량·내역이 정리된 뒤 마지막에 짠다 — 그래서 도메인 자료와 유기적으로 물려야 한다. 리서치가 이걸 추측이 아니라 법정 공식으로 뒷받침한다.

중심축: 법정 공사기간 산정식 = 우리 CPM에 그대로 얹힌다

총공사기간 = 준비기간 + 작업일수 + 비작업일수 + 정리기간
작업일수 = 단위작업 물량 ÷ 1일 생산성(작업량)　·　주공정선(critical path) 상의 작업에 한정
「공공 건설공사의 공사기간 산정기준」(국토교통부고시 제2024-1021호, 시행 2025.1.6) · 「건설기술 진흥법」 제45조의2 — 발주청의 법정 의무[10][11]

⚖️ 왜 이게 결정적인가

  • "단위작업별 물량을 생산성으로 나누어 공기를 산정하며, 전체 공사기간에 영향을 미치는 작업은 주공정선 상에 한정되므로 단위공기 산정도 해당 공종에 한정한다"[11] — 우리 엔진이 이미 주공정을 계산하므로, 검증 대상 공정을 그대로 특정할 수 있다.
  • 1일 생산성(작업량)은 건설공사 표준품셈으로 도출한다[11] → 표준품셈 로컬 DB의 존재 이유.
  • 비작업일수는 월별 기상(혹서·동절·강우·바람·미세먼지) + 공휴일로 산정[12] → 우리 우기 밴드(RainySeason)의 정식 확장 근거.
  • 기준은 작업일수 산정 근거의 문서화를 요구 → "막대 클릭 시 근거 표시"가 실무 요구와 정확히 일치.

기각된 주장 · 냉정한 주의

적대적 검증(주장당 3표)에서 기각된 2건 — 로드맵의 기대치를 과장하지 않기 위해 명시한다.

기각0–3
공개 표준품셈 데이터셋이 공종별 노무·장비·자재 투입량 + 작업량(일작업량)을 그대로 담아 "물량기반 공기 산정기"에 바로 쓸 수 있다는 주장. → 아니오. 문서 추출·구조화가 필요(B2).[7]
기각0–3
S-Construction 2030의 표준품셈·건설기준 디지털화가 자동 물량산출·공사비 산정(+BIM 연계)을 명시적 목적으로 한다는 주장. → 디지털화(1,079개 건설기준)는 사실이나[8], 그 목적 주장은 근거 부족.

⚠️ 실행 시 주의

  • 표준품셈 DB는 "한 번에 전량" 금물 — 주요 공종부터 부분 구축, 커버리지 로그를 남겨 "검증됨/미검증" 구분.
  • 산정식은 주공정선 한정(법정) — 모든 공정에 무차별 적용하면 실무와 어긋난다. 우리 CPM의 critical 플래그를 판정 대상 필터로.
  • 법정 기준 인용은 개정 추적 필요(고시 개정·시행일). 근거 팝업에 조문·개정일 함께 표기.
  • LLM은 끝까지 "제안·설명" — 산정·날짜·주공정은 결정론 엔진이 유일 진실.
