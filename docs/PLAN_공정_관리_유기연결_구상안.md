# 공정 → 관리 유기적 연결 — 구상안 (Sequence 다음 단계)

> 상태: **구상(검토 요청)** · 작성 2026-09-08 · 선행: `PLAN_건설사업관리_모듈_복원_설계.md`(1~3단계 완료)
> 이 문서는 그 설계 §9에 "후속"으로 남겨둔 **모듈↔공정 연계**를 정면으로 다룬다.

## 0. 한 줄 요약

> **공정 id 하나를 모든 관리 모듈이 공유하는 앵커로 삼고, 관리 데이터가 다시 공정표를 움직이게(환류) 만든다.**

지금은 공정표와 관리 모듈이 "같은 앱 안에 나란히" 있다. 다음 단계는 "**하나의 사업으로 맞물려 돌아가게**" 하는 것이다.

## 1. 진단 — 지금 무엇이 끊겨 있나 (코드 실측)

무엇이 이미 되어 있는지부터 정직하게 정리한다.

| 층 | 이미 되는 것 | 근거 |
|---|---|---|
| 백본 | CPM(ES/EF/LS/LF·TF·주공정), 2종 시트(예정/마일스톤), 우기, 미러 | `engine/scheduling.ts`, `types/model.ts` |
| 계획 검증 | 물량÷일작업량 기반 공기 적정성(국토부고시 정합) | `engine/adequacy.ts`, `Task.quantity/unit/workCode` |
| 실적 | 공정별 진척%·담당자·실적착수/완료일, 기간가중 계획대비 | `Task.progress/owner/actualStart/actualFinish` |
| 관리 | 기록형 9종(예산·공사비·자원·품질·안전·문서·인허가·시운전·리스크) | `data/modules.ts`, `RecordModule.tsx` |
| 집계 | 단일 셀렉터 KPI(일정·진척·원가·EVM·경보·기준선 표류), 주간 자동집계 | `engine/projectKpis.ts` |
| 통제 | 변경이력(사유·결재상태)·확정본 버전·AI 검토 라운드트립 | `ChangeEntry`, `BaselineVersion`, ADR-003 |
| 기반 | CRDT 협업·본부 RBAC·조회전용·저장/복원 | `state/crdt.ts`, `authStore.ts` |

**끊긴 지점은 딱 하나로 수렴한다 — 관리 레코드가 공정을 가리키지 않는다.**

```ts
// types/model.ts:260 — 관리 데이터의 전부
export interface ModuleRecord { id: ID; values: Record<string, string> }
```

- `resource.task`("공정/공종"), `quality.category`("공종"), `boq.category`("공종")는 **자유 텍스트**다. 오타 하나면 연결이 끊기고, 공정 이름을 바꾸면 전부 미아가 된다.
- 그래서 집계가 **건수 세기**에서 멈춘다. `projectKpis.ts:364~427`의 경보는 전부 "NCR 3건", "미승인 2건" 수준이고, **어느 공정이 위험한지 말하지 못한다**. (정정: 경보를 눌러도 갈 곳이 없다고 썼으나 사실이 아니다 — `DashboardModule.tsx:208`이 `go(a.module)`로 해당 모듈 뷰까지는 보낸다. 결손은 `ModuleAlert`에 `taskId`가 없어 **공정을 지목하지 못하는 것**이다.)
- EVM도 마찬가지다. `bac = 사업 총예산`, `ev = bac × 기간가중 실적%`(`projectKpis.ts:310~327`) — 사업 전체 한 덩어리라 **공종별 SPI/CPI가 나오지 않는다**. "어디가 새는지"를 못 짚는다.
- 인허가·검측·문서 승인은 실제 현장에서 **공정의 선행조건**인데, 지금은 공정표와 무관한 목록일 뿐이다. 인허가가 밀려도 공정표는 조용하다.

즉 **데이터는 다 있는데, 관계가 없다.** 관계만 넣으면 나머지는 이미 만들어 둔 단일 셀렉터가 다 받아준다.

## 2. 설계 원칙 4가지

1. **백본 불변** — 공정표(CPM)가 유일한 시간 축이다. 모든 관리 데이터는 공정에 매달리고, 공정을 대체하지 않는다.
2. **한 번 입력, 여러 산출** — 현장에서 한 번 찍은 실적이 진척·EVM·주간회의자료·보고서·AI검토·내보내기까지 자동으로 흐른다. 같은 숫자를 두 번 치게 하면 실패한 설계다.
3. **입력은 공정에서, 조회는 어디서나** — 사용자는 "공정을 보다가 그 자리에서" NCR·리스크·검측을 등록한다. 앵커는 그 행위의 **부산물**이지 추가 입력이 아니다.
4. **경보는 반드시 목적지를 갖는다** — 모든 경보는 클릭하면 해당 공정/레코드로 이동하고, 조치는 변경이력에 남는다. 끝나지 않는 경보는 만들지 않는다.

## 3. 구조 — 4층

```
L3 표면    대시보드 · 공정 360 · 오늘의 현장 · 보고서 · 내보내기 · AI검토
              ↑ 구독 (단일 셀렉터)
L2 파생    projectKpis  ← 공정별 롤업으로 확장 (공정 → 공종 → 시트 → 사업)
              ↑ 조인
L1 앵커    ModuleRecord.anchor { sheetId, taskId?, categoryId? }   ◀ 이번에 신설
              ↑ 참조
L0 백본    Task / Link / Category / Sheet  (CPM)
```

핵심은 **L1 한 층을 끼워 넣는 것**이다. L2·L3는 이미 있는 구조를 확장만 하면 된다.

## 4. 다섯 개의 루프 — "유기적"의 실체

유기적이라는 말을 다섯 개의 닫힌 루프로 정의한다. 각 루프는 **입력 → 계산 → 표출 → 조치 → 기록**이 한 바퀴 도는 것을 뜻한다.

### 루프 1. 계획 루프 (물량 → 공기 → 검증)
`BOQ 물량 → 표준 일작업량 → 이론 작업일수 → CPM → 적정성 판정 → 근거 기록`

- 지금: `Task.quantity`를 사람이 따로 입력한다. BOQ 모듈에 같은 수량이 또 있다.
- 앵커 후: **BOQ 레코드를 공정에 걸면 물량이 자동으로 올라온다.** 공사비 내역과 공기 산정 근거가 같은 숫자를 쓰게 된다.
- 산출: "이 공정의 공기 120일 = 물량 3,600㎥ ÷ 일작업량 30㎥/일 + 준비 30일"이 **내역서에서 자동 유도**된다. 발주처 설명이 그대로 된다.

### 루프 2. 실행 루프 (실적 → 진척 → EVM)
`오늘 할 일 → 실적 입력(착수/완료/물량) → 진척% → 공정별 EV/AC → SPI·CPI 롤업`

- 지금: 진척%를 슬라이더로 감으로 넣는다. EVM은 사업 한 덩어리.
- 앵커 후: 진척%를 **물량 진도(시공량 ÷ 총물량)** 로도 산출 가능하고, 공정별 BAC(= 앵커된 BOQ 금액 합)이 생겨 **공종별 SPI/CPI**가 나온다.
- 산출: "터널 공종 SPI 0.82 / CPI 0.95 — 일정은 밀리는데 원가는 아직 괜찮다" 같은 판단이 가능해진다.

### 루프 3. 관문 루프 (승인 → 착수 가능 여부) ★ 가장 현장적인 가치
`인허가·검측·문서 승인 상태 → 후행 공정의 착수 관문 → 미승인이면 공정표에 경고`

- 인허가/문서/검측 레코드에 "이 공정의 선행조건"이라는 관문 지정을 둔다.
- 계산: `task.ES < 관문 승인일` 또는 `승인 미완` → **해당 공정 막대에 관문 경고 표시** + 대시보드 경보.
- 안전장치: **기본은 경고만.** 계획을 임의로 밀지 않는다. 사용자가 "관문 반영"을 켜면 그때 CPM 제약(제약일 = 승인예정일)으로 들어가고, 그 변경은 반드시 변경이력에 사유와 함께 남는다.
- 이게 되면 Sequence는 "그린 공정표"에서 **"착수 가능 여부를 아는 공정표"** 가 된다.

### 루프 4. 경보 루프 (이상 → 조치 → 이력 → 확정본)
`경보 → 클릭 → 해당 공정 360 → 조치(리스크 등록·공기 재산정) → 변경이력 자동 기록 → 확정본`

- 지금 `alerts`는 숫자만 있고 목적지가 없다(`projectKpis.ts:330~429`).
- 앵커 후: 모든 경보가 `taskId`를 갖는다 → 클릭 이동 → 조치 → `appendChange`로 자동 기록.
- 산출: "왜 공기가 늘었나"에 대한 답이 **감사 가능한 사슬**로 남는다. 이건 이미 있는 `ChangeEntry`·`BaselineVersion`이 그대로 받아준다.

### 루프 5. 소통 루프 (주간회의 → AI검토 → 반영)
`주간 자동집계 → 회의 자료 → AI 검토(.md 왕복) → 반영 → 이력`

- `weeklyDigest`(F16)는 이미 착수·완료·지연·다음주 예정을 뽑는다. 여기에 **관문·품질·안전·리스크를 공정별로 얹으면** 주간 공정회의 자료가 그대로 완성된다.
- AI 검토는 현재 duration-only(ADR-003). 앵커가 생기면 **근거를 붙인 진단**으로 확장된다: "3번 공정 지연 — 후행 인허가 미승인 + NCR 2건 + 해당 주 자원 과투입". 뉴로심볼릭 원칙(계산은 코드, 서술은 LLM)은 유지한다.

## 5. 데이터모델 — 구현 후 확정판

> 초안은 아래 세 가지가 틀렸다. 코드 검증(6차원 감사 + 반증)에서 드러나 **구현 전에 고쳤다.**
> 기록으로 남긴다 — 같은 함정을 다시 밟지 않기 위해서다.

```ts
export interface RecordAnchor {
  sheetId?: ID      // ◀ 필수 아님(초안은 필수였다)
  taskId?: ID
  categoryId?: ID
  stamp?: string    // ◀ 신설 — 생성 시점 공정명(판정용 힌트, 식별자 아님)
}

export interface ModuleRecord {
  id: ID
  values: Record<string, string>
  anchor?: RecordAnchor
  // gate 는 넣지 않았다 — M3 에서 '관문 1건 = 레코드 1건'으로 재설계한다.
}
```

**정정 1 — 저장 형태.** 초안은 "레코드 Y.Map에 필드가 느는 것뿐"이라고 했지만, 현재 직렬화
규약에는 `values`의 형제 필드 자리가 **물리적으로 없다**. 쓰기는 `{...record.values}`만 펼치고
(`crdt.ts:393`, `seed.js:163`), 읽기는 Y.Map 전체를 `values`로 흡수한다(`crdt.ts:583`). 타입에만
`anchor`를 추가하면 tsc는 통과하고 런타임에서 100% 소실된다. 그래서 예약키 **`$anchor` 하나에
JSON 문자열로 원자 저장**한다:
- 중첩 객체는 통값 LWW라 동시 편집에서 한쪽 앵커가 임의로 사라진다.
- `sheetId`/`taskId`를 **별도 키로 쪼개면 더 나쁘다** — 필드별로 병합되어 A의 시트 + B의 공정이
  섞인 '다른 시트의 공정을 가리키는' 앵커가 만들어진다. 앵커는 하나의 원자적 결정이므로
  통값 교체가 오히려 올바른 의미다.
- ⚠️ 이 키를 `syncPlainMap`의 `reserved` Set에 **넣으면 안 된다.** reserved는 삭제뿐 아니라
  쓰기까지 건너뛰어(`crdt.ts:192`) 앵커가 최초 값에 영구 고정된다. 직렬화기가 매번 값 또는
  `undefined`를 실어 보내는 방식으로 보호한다.

**정정 2 — `sheetId`는 필수일 수 없다.** `Project.activeSheet` 자체가 optional이고 기본 샘플에는
없다(`sampleProject.ts`). 필수로 두면 위조값을 넣게 되고 그 위조값이 전부 고아로 판정된다.
미지정 = 활성 시트로 해석하며, 정규화는 `engine/anchors.ts`의 resolver 한 곳에서만 한다.

**정정 3 — 고아보다 나쁜 '조용한 오연결'이 있다.** 프리셋 공정 id가 위치 인덱스
(`facilities.ts`의 `fc-{ci}`·`ft-{ci}-{ri}-{si}`)이고 시트 id가 리터럴(`'sh-cons'`)이라,
**다른 시설물 템플릿으로 바꿔도 세 필드가 전부 일치해 무결성 검사를 통과한다.** 고아 신호가
0인 채로 '터널 굴착 NCR'이 '수압관로 용접'에 붙는다. `stamp`(생성 시점 이름) 대조가 이걸 잡는
유일한 신호이며, 불일치는 '확인 필요'로만 강등하고 **자동 해제는 하지 않는다.**

앵커 상태는 2종(정상/고아)이 아니라 **4종**이다: `linked` · `otherSheet`(다른 시트 — 깨진 게
아니다) · `needsCheck`(stamp 불일치) · `orphan`. 여기에 '앵커 없음'(사업 단위)은 경고가 아닌
중립 상태로 따로 둔다.

- `Task`는 **건드리지 않는다.** 역방향(공정 → 레코드)은 `buildByTaskIndex`로 만든다.
- 고아 앵커는 **절대 자동 정리하지 않는다.** 레코드는 살아남고 재지정을 기다린다.
- resolver는 **문서 전체 검색을 금지**하고 시트 스코프로 한정한다 — 서버 시드가 `root/tasks`와
  `root/sheets/*/tasks`에 같은 id를 중복 기록해서, 전체 검색은 화면에 없는 죽은 사본을
  '정상 연결'로 오판한다.

## 6. 화면 — 3개만 새로 만든다

### (1) 공정 360 — 인스펙터 탭 ★ 최우선
공정 하나를 선택하면 그 공정에 걸린 **모든 것**이 한 화면에:
```
[3-2 터널 굴착]  계획 04-01~07-28 (120일) · 실적 42% (계획比 −8%p) · 담당 김OO
├ 물량   3,600㎥ ÷ 30㎥/일 = 120일  (적정성 ±0%)   [BOQ 2건 ▸]
├ 사업비 BAC 1,240,000천원 · AC 980,000천원 · CPI 0.95
├ 관문   ⛔ 실시계획 변경인가 미승인 (예정 03-20)   ▸
├ 품질   NCR 1건(미조치) · 검측 3건 합격            ▸
├ 안전   고위험 1건                                   ▸
├ 자원   금주 12인·굴착기 2대                         ▸
└ 리스크 지반 불량 (영향 상 / 열림)                  ▸
[＋ 이 공정에 검측·NCR·리스크·자원 추가]
```
`＋` 버튼이 앵커를 자동으로 채운다 → **사용자는 앵커의 존재를 모른 채 앵커를 만든다.** 원칙 3의 구현.

### (2) 오늘의 현장 — 담당자 진입점
`owner == 나`인 공정 중 **오늘 착수/완료 예정 · 지연 · 승인 대기 관문**만 카드로. 본부 RBAC이 이미 있으니 필터만 얹으면 된다. 관리자는 기존 대시보드로 간다(역할별 홈).

### (3) 대시보드 확장
경보를 **공정 지목형**으로 교체(클릭 이동), 공종별 SPI/CPI 표, 관문 현황 밴드 추가.

> 기존 화면(공정관리·진척·기록 9종·보고서·변경이력)은 **그대로 둔다.** 앵커 열 하나가 늘 뿐이다.

| **M1** 앵커 기반 ✅ | 아래 10단계 — 선결 데이터 소실 차단 2건 포함 | 레코드가 공정에 붙는다 | tsc · 스모크 8종 · collab-smoke · mount-test |

각 단계는 **독립적으로 배포 가능**하다. M1만 나가도 "공정별 조회"라는 가치가 선다. M3에서 멈춰도 손해가 없다.

### M1 실제 구현 순서 (완료)

앵커를 얹기 전에 **관리 기록이 조용히 사라지는 경로 두 개**를 먼저 막아야 했다. 둘 다
스모크로 재현해 확인했고, 수정 전에는 실패하고 후에는 통과하는 테스트로 고정했다.

| # | 단계 | 핵심 |
|---|---|---|
| 1 | 회귀 그물 | 모듈 레코드 왕복 기준선(소스 변경 0). **여기서 실제 버그 3건이 드러났다** |
| 2 | 쓰기 그림자 신선도 | `observeRoot`에 modules·baseline·changeLog·baselineVersions 추가 — **원격 기록이 로컬 편집 한 번에 삭제되던 것** |
| 3 | 모델 | `RecordAnchor`(sheetId optional + stamp), SCHEMA_VERSION 5 |
| 4 | CRDT 대칭 | `$anchor` 인코딩 — 클라 2곳 + 서버 2곳 |
| 5 | 레거시 승격 | 구버전이 `values['$anchor']`에 가둬 저장한 앵커를 복원 |
| 6 | 모듈 합집합 보호 | **템플릿 한 번 바꾸면 예산·NCR·인허가가 전부 사라지던 것** |
| 7 | store 액션 | `setRecordAnchor`/`clearRecordAnchor` + readOnly 규약 |
| 8 | 앵커 해석기 | `engine/anchors.ts` — 4종 상태 · 전 시트 resolver · byTask 인덱스 |
| 9 | BOQ 자동 앵커 | 취입 매핑이 이미 있는데 버려지고 있었다 → **사용자 입력 0으로 앵커 생성** |

M1의 UI는 의도적으로 **조회 + 자동 생성**으로 좁혔다. 앵커를 손으로 거는 피커는 M2(공정 360)의

만들고, 기록 표는 이미 가로 스크롤 경계에 있다.

## 8. 검증 기준 (완료 판정)

- 앵커된 레코드가 2인 동시편집에서 병합된다(collab-smoke). ✅
- 공정 삭제 → 레코드 생존 + 고아 배지. 재지정 UI는 M2. ✅(생존·배지)
- **SPI/CPI는 합산이 정의되지 않는다**(무차원 비율). 롤업 불변식은 금액에 대해서만 쓴다 —
  `Σ BAC_i == BAC` · `Σ PV_i == PV` · `Σ EV_i == EV` · `Σ AC_i == AC`, 그리고 'SPI/CPI는 롤업
  합에서 **재계산한** 비율이 사업 값과 일치'로 검증한다. (초안 문구는 기계적으로 검증 불가였다.)
- 관문 OFF 상태에서 기존 CPM 결과가 **비트 단위로 동일**(회귀 0). — M3
- 조회전용 사용자: 전부 열람 가능, 앵커/관문 편집만 비활성. ✅

### 미해결 — 별도 슬라이스로 분리한 것

**모듈 컨테이너 동시 생성 경쟁(데이터 소실).** 아직 없는 모듈을 두 사람이 **처음** 열어 동시에
기록하면 한쪽 기록이 통째로 사라진다. `root/modules` 안의 모듈 컬렉션이 중첩 Y.Map이라 키 단위
LWW로 컨테이너 자체가 교체되기 때문이다 — `bootstrapProjectYTypes`가 최상위 컨테이너에 대해
해결해 둔 "nested-type replacement trap"이 여기엔 적용되지 않았다.

- 재현: 이미 있는 컬렉션에 동시 추가는 정상 병합(`[mr-seed, mr-A, mr-B]`), 신규 컬렉션 동시 생성은
  `[mr-B]`만 남음. `crdt-smoke`에 **특성화 테스트로 현재 동작을 고정**해 두었다(통과 = 아직 안 고쳐짐).
- 근본 수정은 모듈별 최상위 named type 또는 복합키 평탄화 — 둘 다 **저장 레이아웃 변경**이라
  배포 중 구·신 클라이언트가 섞이면 데이터가 갈린다. 마이그레이션 계획과 배포 절차가 함께
  필요하다.

**BOQ 재취입 멱등성.** `importBoqQuantities`가 행을 무조건 push 하고 이전 취입분을 치환하지 않아
연속 2회 [반영]이면 레코드가 중복 누적된다. 앵커 자체는 영향받지 않지만(레코드마다 독립 앵커),
M4의 `Σ taskBAC == 공사비 예산` 불변식이 취입 횟수만큼 부풀어 깨진다 — **M4 착수 전 필수 선결.**

### M3 관문(gate) 스키마 — 확정

초안의 `gate: { taskIds: ID[]; dueISO?: string }`은 **폐기한다.** CRDT에서 배열은 통값으로 교체되어
(`crdt.ts`의 `syncPlainMap`), 두 사람이 각자 다른 후행 공정을 관문에 추가하면 나중 쓰기가 상대의
추가를 경고 없이 지운다. `changeLog.taskIds`가 배열 통값을 허용하는 근거는 'append 후 불변'인데,
관문은 계속 고쳐지는 집합이라 그 예외에 해당하지 않는다.

**확정안 — 관문 1건 = 레코드 1건.** 관문을 `ModuleRecord`와 같은 레코드 컬렉션으로 저장한다:

```
gate 레코드 = { id, values: { sourceModule, sourceRecordId, taskId, dueISO, kind } }
```

- 한 문서가 공정 셋을 막으면 레코드 3건이 된다. 두 사람이 각각 다른 공정을 추가하면 **서로 다른
  레코드 id**라 기존 레코드 병합 규칙이 그대로 먹는다(경합 자체가 생기지 않는다).
- 저장 위치는 `Project.modules`의 전용 moduleId(`gate`)를 쓴다 → `setModuleRecords` ·
  `orderedModuleRecords` · 합집합 보호 · 서버 대칭이 **전부 재사용**되어 추가 CRDT 작업이 0이다.
- 해제는 레코드 삭제. `taskIds` 배열을 고쳐 쓰는 연산이 사라지므로 동시 편집 소실 경로도 사라진다.

이 결정으로 M3는 '스키마 설계'가 아니라 '판정 로직 + 표시'만 남는다.

### 첨부 문서 보존 정책 — 결정에 필요한 것

이건 코드로 선행할 수 없다. 회사 기준이 필요한 결정이라 **현재 동작만 명시**하고 열어 둔다.

| 질문 | 현재 동작(실측) | 결정 필요 |
|---|---|---|
| 프로젝트를 지우면 첨부도 지우나 | `server/data/documents/<projectId>/`에 **그대로 남는다** | 함께 삭제 / 보관 후 만료 / 영구 보존 |
| 레코드를 지우면 그 첨부는 | 남는다(고아 blob) | 정리 주기 |
| 개정(rev) 이력 | 문서 대장의 `rev` 필드는 **표시용 문자열**, 파일 버전은 따로 없다 | 파일 버전 보관 여부 |

정책이 정해지기 전에 임의로 삭제 로직을 넣지 않는다 — 되돌릴 수 없는 쪽으로 기우는 기본값은
위험하다. 그때까지 `server/data/`는 버전 관리 대상이 아님을 분명히 해 둔다(업로드 blob이 커밋에
섞여 들어간 사고가 실제로 있었다).

**결정 필요:** ① M2(공정 360)로 바로 갈지, 위 컨테이너 경쟁 수정을 먼저 할지 ② 관문 CPM 반영을
아예 넣을지(경고만으로 끝낼지) ③ 물량 기반 진척을 M4에 넣을지 별도로 뺄지.
