HydroNet · 기술 자문 검토

전문가 피드백 반영 검토 보고서

외부 전문가가 주신 8개 항목의 조언을 HydroNet 실제 코드베이스에 대조하고, 웹 리서치로 사실을 확인한 뒤, 각 항목을 어떻게 반영할지를 정리했습니다. 핵심 주장 6건은 3표 적대(反論) 검증으로 교차 확인했습니다.

작성일 2026-07-06 대상 브랜치 dev (포트 4020) 현재 스택 React 18 · Vite 6 · TS 5.7 · zustand 5 · Express(ESM) 검증 방식 코드 대조 + 웹 리서치 26개 에이전트 · 6주장×3표 검증

01한눈에 보기

전반적으로 전문가의 조언은 정확하고 대부분 채택 권장입니다. 단, 두 곳에 사실 정정이 있습니다 — ① Node 강제는 “24 이상”이 아니라 “Node 24.x LTS”로 좁혀야 하고, ② Tauri의 이점은 번들 크기이지 Windows에서의 메모리가 아닙니다(아래 검증 참조).

02사실 검증 결과 (6 주장 · 각 3표 적대 검증)

각 주장을 3명의 검증관이 “반박 시도” 관점으로 최신 공식 소스를 확인했습니다. 2표 이상 반박이면 기각. 결과: 5건 지지, 1건 반박.

지지 3 · 반박 0

Node.js 24(Krypton)는 2026-07 기준 활성(Active) LTS다.

✔ 2025-10-28 Active LTS 진입, 2026-10-20 유지보수 전환, EOL 2028-04-30. 2026-07 시점 유일한 Active LTS.

⚠︎ 정밀화: “24 이상” 강제는 부정확 — Node 26은 비-LTS(Current)라 “Node 24.x LTS(>=24 <25)”로 좁혀야 함.

지지 3 · 반박 0

Vite 8은 별도 설정 없이 기본 번들러로 Rolldown을 쓴다.

✔ 2026-03-12 정식 출시. 공식 문구 “Rolldown is the default bundler, for everyone, with no opt-in.” Vite 7 이하는 Rollup.

➕ 정밀화: Rolldown은 Rollup뿐 아니라 개발용 esbuild까지 대체(→Oxc). HydroNet은 Vite 6이므로 아직 Rollup.

지지 3 · 반박 0

Rolldown은 Rollup 대비 빌드가 유의미하게 빠르다.

✔ 공식 10~30배(규모 클수록 확대). 벤치 10,000모듈: OS별 20~53배.

⚠︎ 단, 이는 빌드 시간일 뿐 사용자 체감 성능 아님. 소규모 drop-in은 ~1.8배로 낮아질 수 있음. HydroNet은 소형이라 절대이득 작음.

지지 3 · 반박 0

Biome 2.x는 린트+포맷 단일 도구로 ESLint+Prettier를 상당 부분 대체한다.

✔ 단일 Rust 바이너리, 500+ 규칙, Prettier ~97% 호환, biome migrate 제공.

⚠︎ 타입 인식 린트는 opt-in·부분 커버리지. 타입체크는 대체 못 함 → tsc --noEmit 유지 필수.

반박 3 · 지지 0

Tauri는 Electron 대비 메모리·번들 모두 현저히 작다.

✔ 번들 크기는 전 플랫폼에서 사실(빈 앱 ~3MB vs ~374MB).

✘ 메모리는 조건부. Windows는 Tauri의 WebView2도 Chromium이라 Electron과 대등(공유메모리 반영 시). 큰 이득은 macOS/Linux 한정. → HydroNet(Windows)엔 “메모리 이득” 미적용.

지지 3 · 반박 0

GitHub은 README의 ```mermaid 블록을 네이티브 렌더링한다.

✔ 2022-02-14부터 Issues·PR·Wiki·Markdown 파일에서 기본 지원(플러그인·빌드 불필요, 라이브 렌더).

➕ 서드파티 mermaid 플러그인은 오히려 충돌 유발 → 순정으로 충분.

03항목별 상세 검토 & 반영 방안

각 항목: 사실 확인 → HydroNet 현재 상태 → 어떻게 반영 순서.

① Biome — 린트·포맷·코드체크 자동화

채택우선순위 중난이도 낮음

전문가 지적대로 HydroNet엔 린터·포매터가 하나도 없습니다(설정 파일 0건 확인). Biome는 Rust 단일 바이너리로 ESLint+Prettier를 상당 부분 대체하며, 이미 package.json이 있으니 devDependency로 버전을 고정해 설치하는 것이 정석입니다.

  • 2026-07 최신 안정판 v2.5.x(500+ 규칙). Prettier ~97% 호환 + organizeImports 내장.
  • HydroNet은 루트에서 npm --prefix로 client(TS/JSX)+server(순수 JS ESM)를 묶는 얕은 모노레포 → 루트 biome.json 하나로 둘 다 커버 가능.
  • 주의: Biome는 타입체크를 대체하지 않음. client의 build는 tsc --noEmit && vite build 그대로 유지.
  • 타입 인식 린트(noFloatingPromises 등)는 파일 스캐너 필요·opt-in → 처음엔 켜지 말고 recommended+포맷+import 정리만으로 시작.
이렇게 반영
  1. 루트에서 npm i -D --save-exact @biomejs/biome → npx @biomejs/biome init.
  2. biome.json에 files.includes로 HydroNet.html(~20MB)·*.mp4·dist·node_modules·*.log 강제 제외(성능·오탐 방지).
  3. server 전용 완화는 overrides: [{ includes:["server/**"], ... }]로.
  4. 루트 scripts에 lint / format / check 추가. 첫 biome check --write 대규모 재포맷은 기능 커밋과 분리해 단독 커밋.
  5. (나중) GitHub Actions에 biomejs/setup-biome@v2 + biome ci . 게이트.

② Electron 전환 — 지금은 보류, 웹부터

조언 타당우선순위 낮음

전문가 조언(“웹 기능·사용성부터, 패키징은 나중”)은 HydroNet 현 상태에 정확히 맞습니다. 패키징은 “얇은 껍데기” 작업이라 나중에 붙여도 마이그레이션 비용이 낮은 반면, 지금 하면 Electron의 성능 최적화 부채(require()·V8 스냅샷·150~300MB 메모리)를 조기에 떠안습니다.

검증 반박 — Tauri 오해 주의

“Tauri가 Electron보다 가볍다”는 번들 크기에만 무조건 참입니다. 메모리는 조건부로, Windows에서는 Tauri의 WebView2도 Chromium 계열이라 Electron과 대등합니다. HydroNet의 .exe 타깃이 Windows라면 메모리 이점은 사실상 없다고 보고 판단하세요.

  • “설치형처럼 보이기”만이 목적이면 지금은 PWA로 저비용 달성: web manifest + display:standalone + 최소 서비스워커 → Edge/Chrome “앱 설치”로 바탕화면 아이콘·독립 창.
  • 단, PWA는 LAN Express(HTTP 오리진) 경로에만 붙이세요. 순수 file:// 단일 HTML은 설치 프롬프트가 제한됩니다.
  • 진짜 .exe(설치관리자·오토업데이트)가 필요해지면 Tauri v2가 1순위(React 코드 그대로 감쌈, devUrl+frontendDist만). Electron은 이 규모엔 과함.
  • 다행히 네이티브 의존 @resvg/resvg-js는 빌드 스크립트 전용이라 데스크톱 패키징의 블로커가 아님. 런타임은 jspdf(순수 브라우저)+File System Access.
이렇게 반영
  1. 지금: memory.md/README 로드맵에 “Electron 미채택, .exe 필요 시 Tauri v2 1순위”로 방향 고정.
  2. 지금(반나절): LAN 경로에 manifest.webmanifest+아이콘+최소 SW 추가 → “설치형 느낌” 확보(단일 HTML 빌드엔 미포함).
  3. 나중(트리거 시): npm i -D @tauri-apps/cli → tauri init. macOS 배포까지 간다면 SVG 필터/PDF를 WKWebView에서 회귀 테스트.

④ Node 24 LTS 강제 — 단, “24.x LTS”로

채택문구 정정난이도 낮음

Node 24는 2026-07 기준 유일한 Active LTS가 맞고(검증 3/0), 로컬이 이미 24.14.1이라 사실상 “문서화·강제”만 남은 저위험 작업입니다. 다만 검증에서 나온 정정 하나:

문구 정정

“Node 24 이상”을 문자 그대로 강제하면 비-LTS인 Node 26(Current)까지 허용되어 LTS 안정성 논리와 어긋납니다. 정확한 강제 범위는 "node": ">=24 <25"(24.x LTS로 고정, 패치는 자동 수용).

  • 현재 engines·.nvmrc·.npmrc·CI 전무 → “강제”가 실제로 걸려 있지 않음.
  • 견고한 강제 = 3계층: ⓐ .nvmrc(단일 진실원천) ⓑ 3개 package.json의 engines + 루트 .npmrc engine-strict=true(설치 하드 실패) ⓒ (나중) CI가 같은 파일을 node-version-file로 읽어 검증.
  • 루트 postinstall이 client/server로 재귀 install → engines를 3곳 모두에 넣어야 하위 설치에서도 걸림.
  • 호환성 OK: Vite 6/7/8·React 18·TS 5.7·jsdom·Express 4 모두 Node 24와 문제 없음.
운영 환경 확인

engine-strict=true를 켜기 전, 전무님 운영 PC(포트 4000)의 Node가 24 이상인지 먼저 확인하세요. 낮으면 그쪽 npm install이 하드 실패합니다. (운영 폴더는 미변경 원칙이지만 설치 실패 방지 차원.)

이렇게 반영 (dev 폴더에서만, git push origin dev)
  1. 루트 .nvmrc 생성 → 내용 24.
  2. root/client/server package.json에 "engines": { "node": ">=24 <25", "npm": ">=11" }.
  3. 루트 .npmrc에 engine-strict=true.
  4. 검증: npm run build + smoke.ts + mount-test.ts 통과 → README 갱신 → 커밋.

⑤ Vite / Rolldown — 지적은 정확, 전환은 단계적으로

사실확인우선순위 낮음~중난이도 중

전문가 지적이 정확합니다. Vite 8(2026-03-12 출시)부터 Rolldown이 opt-in 없이 기본 번들러가 맞고(검증 3/0), client/vite.config.ts 확인 결과 HydroNet은 Vite 6 → Rollup을 쓰고 있습니다(아직 Rolldown 아님). “쓰고 있는지 확인” → 답: 아니오.

지금 Vite 8로 점프하지 말 것 — 이유

배포의 핵심인 19.5MB 단일 HTML(build:single)이 rollupOptions.output.format:'iife' + inlineDynamicImports + vite-plugin-singlefile에 의존합니다. Rolldown은 IIFE를 지원하지만 import.meta.url 폴리필을 제거(→undefined)하는 등 미묘한 차이가 있어 file:// 단일 HTML이 조용히 깨질 수 있습니다. 게다가 HydroNet은 소형이라 10~30배 이득의 절대 체감이 작습니다.

  • 성능차는 빌드 시간 얘기지 사용자 체감 아님. 소형 앱은 이미 빌드가 짧아 실이득 제한적.
  • Vite 8 요구: Node 20.19+/22.12+ (④의 Node 고정과 함께 처리하면 무통증).
  • vite-plugin-singlefile ^2.3.3의 Vite 8/Rolldown 호환은 별도 실빌드 검증 필요(미확인).
이렇게 반영 (단계적)
  1. 먼저 dev에서 Vite 6→7 승격 + engines/.nvmrc 고정 → build+smoke+mount+build:single 4종 통과.
  2. 비파괴 시험: "vite": "npm:rolldown-vite@<고정버전>" alias로 교체(@latest 금지).
  3. 가장 중요: SINGLE=1 재빌드 후 브라우저 file://에서 SVG·PDF·저장·폰트 실동작 확인. 빌드 경고(IIFE/미지원 옵션) 스캔.
  4. 깨끗하면 유지·나중에 Vite 8 승격, 아니면 alias 롤백(그냥 Vite 7 유지). 모든 시험은 dev/4020, 운영 4000 미접촉.

⑥ CRDT 라이브러리 — Yjs 1순위

Yjs 권장우선순위 중난이도 중~높음

HydroNet엔 협업/동기화 계층이 전혀 없어(단일 사용자·전체 스냅샷) CRDT는 “해볼 만한” 정도가 아니라 다중 편집을 원하면 사실상 필수 경로입니다. 라이브러리는 Yjs를 1순위로 권합니다.

왜 Yjs인가

  • 배포 정합: 순수 JS(WASM 없음) → vite-plugin-singlefile IIFE·file://·Electron에 마찰 0. (Loro/Automerge는 WASM이라 단일 HTML 로딩 검증 부담)
  • local-first + LAN: y-indexeddb(오프라인)+y-websocket(기존 Express에 ws만 얹으면 dumb relay).
  • undo 정합: 기존 undo/redo를 Y.UndoManager+trackedOrigins로 “내 편집만” 되돌리게 표준 교체.
  • zustand 통합: Y.Doc=진실원본, zustand=파생 뷰 패턴 성숙.

2·3순위

  • Loro(1.13.x) — 강력한 2순위. Movable List/Tree가 HydroNet의 재정렬·계층 구조와 개념적으로 최적. 단 WASM·생태계 얇음. 성능/재정렬 정확성이 병목이면 승격 검토.
  • Automerge 3.x — 변경 이력·브랜치가 제품 기능일 때만(설계 리뷰 이력 등). 번들·WASM 비용.
  • 참고: “Loro 프로덕션 비권장/Automerge 2.x”류 서술은 낡은 정보. Loro는 1.0부터 포맷 안정화, Automerge는 3.x.

⑦ CRDT를 어디에 붙이나 + 이슈 초안

분석 완료이슈 초안 제공

실제 코드(store.ts·model.ts·api.ts·fileIO.ts·server/src/index.js)를 읽고 분석했습니다. 핵심 결론:

붙일 지점 = 단일 쓰기 관문

모든 도메인 변경이 store.ts의 내부 commit(mutate, opts) 한 곳을 통과합니다(clone→mutate→applyCascade→withSchedule→set). 여기가 유일한 쓰기 지점이라, project를 Y.Doc로 보유하고 commit의 mutate(draft)를 doc.transact(...)의 요소 단위 변형으로 바꾸면 나머지 액션 시그니처·렌더 레이어는 그대로 두고 내부만 CRDT화할 수 있습니다.

#위치무엇을난이도
1store.ts commit()/projectproject를 Y.Doc로(rootMap + tasks/links/categories = Y.Array<Y.Map>), mutate를 doc.transact 요소변형으로높음
2store.ts undo/redopast/future 스냅샷 스택 → Y.UndoManager중간
3server/src/index.js전체-파일 PUT과 별개로 y-websocket provider(room=projectId) + 서버 영속높음
4api.ts/fileIO.ts.json(평면)↔Y.Doc 스냅샷 이중 저장·어댑터중간
최대 리스크 — 파생 스케줄 ↔ CRDT 진동

withSchedule/applyCascade는 한 편집으로 다수 Task의 start를 연쇄 이동합니다. 이 결과를 CRDT에 다시 쓰면 두 사용자가 서로의 cascade를 덮어써 진동합니다. 원칙: 권위 데이터 = 사용자가 실제 입력한 start/duration/lag/type·링크 존재만. cascade/CPM 결과(es/ef/critical/__mirror)는 CRDT에 저장하지 않고 각 클라이언트가 로컬 계산. (다행히 이 파생값들은 코드에서 이미 “비영속”으로 분리돼 있어 경계가 뚜렷합니다.)

## 배경 / 목적

HydroNet은 현재 **단일 사용자·단일 `Project` 문서·전체 스냅샷** 편집 도구다. 향후
LAN 다중 편집(현장 사무소에서 여러 PC가 같은 공정표를 동시 편집)을 위해
**CRDT(Yjs) 도입 지점과 단계적 로드맵**을 확정하고자 한다. 실제 코드(store.ts,
model.ts, api.ts, fileIO.ts, server/src/index.js)를 읽고 정리한 결과를 붙이니
전문가 검토·코멘트를 부탁드린다.

> 리포 호스트는 GitHub(hjlee624/HydroNet). (일부 논의에서 Gitea MCP 언급이 있었으나 실제 호스트는 GitHub.)

## 현재 구조 (그라운드 트루스)

- 상태관리: 앱 전체가 zustand 스토어 하나(useEditor), 편집 문서 project: Project가 통째로 그 안에.
- 유일한 쓰기 지점: 모든 변경이 store.ts의 commit(mutate, opts)을 통과
  (clone → mutate(draft) → applyCascade → withSchedule로 CPM 재계산 → set). 변경 단위=문서 전체.
- Undo/Redo: CRDT 아님. 전체 문서 스냅샷 스택(past/future, HISTORY_LIMIT=50).
- 문서 구조(model.ts): categories[]/tasks[]/links[]/rainySeasons[]가 안정 id(nanoid) 리스트 컬렉션.
  멀티시트는 활성 시트만 최상위, switchSheet가 swap. es/ef/ls/lf/critical·__mirror는 계산/표시 전용(비영속).
- 저장: 사용자가 '저장' 시. fileIO.ts가 File System Access로 project 전체를 .json.
  api.ts는 전체 문서 PUT /api/projects/:id + localStorage 폴백.
- 서버(index.js): 얇은 Express. PUT = 원자적 전체-파일 교체, 병합 없음(last-write-wins).
  동기화/웹소켓/프레즌스 계층 전무.

즉 CRDT 도입 = '전체 교체 파이프라인(commit·past/future·setProject·PUT)'을 '요소 단위 op'로 바꾸는 일.

## 후보 지점

|---|------|--------|--------|

| 2 | store.ts undo/redo | past/future → Y.UndoManager | 중간 |

## 추천: Yjs (+ y-websocket, y-indexeddb, Y.UndoManager)

- Y.Array<Y.Map>가 현재 id 기반 리스트 컬렉션에 1:1 대응(서로 다른 Task 편집=필드 병합, 동일 필드만 LWW).
- 순수 JS → 단일 HTML(IIFE)·file://·Electron 상성 좋음. y-indexeddb만으로 provider 없는 오프라인 영속 가능.
- (Automerge는 WASM 의존이라 단일 HTML 부담, Loro는 유망하나 생태계 성숙도 미흡 → 리스크 최소화 위해 Yjs 1순위.)

## 로드맵

0. 경계 고정(비파괴): withSchedule/applyCascade 산출(es/ef/…/__mirror)을 '동기화 제외'로 명문화.
1. 로컬 데이터모델 CRDT화(provider 없음): project 보유를 Y.Doc로, commit을 doc.transact로,
   observeDeep→withSchedule→zustand 평면 push로 렌더 무변경. y-indexeddb 로컬 영속. → build+smoke+mount 통과.
2. undo/redo 이관: past/future → Y.UndoManager, CPM 재계산은 비추적 origin 격리.
3. provider(서버 동기): index.js에 y-websocket ws 업그레이드. 기존 전체-파일 PUT은 스냅샷/백업으로 강등. 오프라인은 provider 미부착.
4. 프레즌스: awareness로 원격 커서·선택(기존 selectedTaskIds/selectedCategoryIds 활용).
5. 배포/호환 마감: .json↔Y.Doc 무손실 변환기(schemaVersion 분기), LWW PUT 제거/read-only화.

## 리스크

- 파생 스케줄 ↔ CRDT 진동: 권위데이터=사용자 입력값만, cascade/withSchedule는 로컬 계산으로.
- 멀티시트: 활성 시트만 최상위+swap 구조는 CRDT와 궁합 나쁨 → 모든 시트 Y.Doc 상주, '활성 시트'는 로컬 뷰로.
- 오프라인 배포: 단일 HTML/file://에서 provider 상시 on 불가 → 옵션화 필수.
- 저장 포맷 이원화: 평면 .json ↔ CRDT update(binary) 왕복 무손실.
- undo 시맨틱 변화: 전역 undo → '내 변경만'. 단일사용자 UX 회귀 검증.
- 서버 LWW PUT 잔존: provider 후에도 남으면 CRDT를 덮어씀 → 강등/제거.

⑧ 이슈 자동 생성 — Gitea MCP가 아니라 GitHub로

GitHub로 대체난이도 낮음

전문가가 언급한 gitea-mcp는 실재하고 이슈 생성도 지원합니다. 하지만 HydroNet의 정식 호스트는 GitHub(hjlee624/HydroNet)이고 gh CLI가 이미 repo/workflow 스코프로 인증돼 있어, Gitea로 옮길 이유가 없습니다(gitea.hmac.kr 미러 remote가 있으나 origin은 GitHub). GitHub 진영에 완전히 동등한 수단이 있습니다.

  • 가벼운 기본안 = gh CLI: 추가 설치·MCP 등록 0. Claude가 코드를 읽어 이슈 본문을 파일로 쓰고 gh issue create -F 호출. 단일 개발자엔 이게 마찰 최소.
  • 정식/확장안 = GitHub 공식 MCP(remote): 이슈+PR+라벨+서브이슈까지. claude mcp add --transport http github https://api.githubcopilot.com/mcp/. 툴 단위 로드로 컨텍스트 절감.
  • “AI가 코드 분석해 이슈 자동생성”의 실체 = 탐색 에이전트가 근거 뽑고 → 본문 작성 → gh issue create. 바로 ⑦의 CRDT 이슈가 그 산출물입니다.
  • 주의: 이슈 생성 API는 자동 재시도가 없어 중복 생성 위험 → 드래프트→사람 리뷰→발행 게이트 권장.
이렇게 반영
  1. 추가 설정 없이 즉시 가능: ⑦의 이슈 초안을 검토 후 gh issue create -R hjlee624/HydroNet -t "..." -F issue-crdt.md -l "enhancement,architecture".
  2. (선택) .github/ISSUE_TEMPLATE에 “아키텍처 변경” 템플릿(문제/영향파일/제안/수용기준/리스크/spike) 추가 → 에이전트가 채울 골격.
  3. Gitea 미러는 백업으로만 두고, 이슈·정식 워크플로는 GitHub(origin dev)에서.
